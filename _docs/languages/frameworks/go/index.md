## Big Picture

Go ships with a strong standard library (`net/http`, `database/sql`), so framework adoption should solve specific pain points rather than add abstraction for its own sake.

This section focuses on popular, practical options:

- API framework: `gin`
- API framework with stronger middleware ergonomics: `echo`
- ORM/data access framework: `gorm`

## Quick Selection

| Need | Strong first choice |
| --- | --- |
| fast REST API with simple ergonomics | `gin` |
| structured middleware + validation hooks | `echo` |
| ORM with migrations/model mapping | `gorm` |
| max control/min abstraction | stdlib `net/http` + `database/sql` |

## Architecture Playbooks

### CRUD/API service

- framework: `gin` or `echo`
- persistence: `gorm` (if ORM productivity is worth abstraction)
- fallback for critical SQL paths: `database/sql` and explicit queries

### Throughput-sensitive service

- start with stdlib `net/http` + minimal middleware
- adopt framework features selectively where they materially reduce complexity

## Operational Guidance

1. Treat contexts as first-class API parameters for cancellation/timeouts.
2. Keep middleware chains explicit and documented.
3. Verify SQL generated by ORM for critical queries.
4. Add race detector and load tests before release.

## Detailed Selection Guide

| Goal | First choice | Why | Caveat |
| --- | --- | --- | --- |
| straightforward REST API | `gin` | quick routing/binding and broad community usage | easy to over-pack handlers with business logic |
| middleware-rich API lifecycle | `echo` | clean middleware and centralized error handling hooks | still need explicit validation and context discipline |
| productive ORM workflow | `gorm` | rapid CRUD + associations + transactions | must inspect generated SQL for critical paths |
| max control/perf | stdlib `net/http` + `database/sql` | minimal abstraction and explicit behavior | more plumbing effort |

## Architecture Blueprints

### API service (framework-first)

- router/framework: Gin or Echo
- transport layer: request binding + response mapping only
- service layer: business policy (no HTTP framework types)
- repository layer: GORM or explicit SQL
- observability: structured logs + metrics middleware

### API service (stdlib-first with selective framework usage)

- start from `net/http` handlers
- add framework only for high-value concerns (validation, middleware ergonomics)
- keep context propagation and timeout policy identical regardless of framework

### Data-heavy CRUD service

- GORM for common CRUD and relation loading
- fall back to raw SQL for performance-critical queries
- add query-count and query-latency instrumentation at repository boundary

## Operational Checklist (Go Track)

1. Every request path carries `context.Context` to DB and outbound clients.
2. Timeout budgets defined at ingress and honored downstream.
3. Middleware order documented and covered with tests.
4. GORM-generated SQL sampled and reviewed for key endpoints.
5. Race detector (`-race`) and load tests are part of CI release gate.

## Common Pitfalls

1. Treating framework bind result as fully validated domain object.
2. Returning raw internal errors directly to HTTP clients.
3. Mixing transaction and network calls in the same long-lived context.
4. Overusing global mutable state without synchronization boundaries.
